1. EXECUTIVE SUMMARY & FORWARD DEPLOYED ENGINEER (FDE) PHILOSOPHY
================================================================================

PressLens is a specialized AI-powered football tactical intelligence system.
It converts raw match events, player positional coordinates, and pressing dynamics
into grounded, mathematically verified tactical insights and fan-accessible explanations.

WHAT A FORWARD DEPLOYED ENGINEER (FDE) DOES:
An FDE sits at the intersection of production software engineering, domain problems,
and state-of-the-art AI. Rather than building speculative research demos or fragile
wrappers around LLM prompts, an FDE builds dependable, high-impact software that
solves a concrete user problem reliably.

In football analysis, naive LLM implementations fail completely because:
1. LLMs cannot compute geometry: An LLM prompted with 22 (x, y) coordinates will
   hallucinate distances, miscalculate convex hulls, and invent non-existent passing lanes.
2. LLMs hallucinate domain theory: Without strict grounding, models fabricate tactical
   terminology or offer generic clichés ("they need more desire").
3. LLMs are fragile: API timeouts, rate limits, or JSON formatting errors break user workflows.
4. Fans are overwhelmed by raw analytics: Ordinary fans cannot interpret convex hull
   areas or raw tracking vectors without intuitive visual context.

HOW PRESSLENS EMBODIES FDE EXCELLENCE:
- Strict Deterministic Separation: All spatial mathematics, Euclidean distances,
  convex hull compactness, pressing vectors, and cover shadow cone geometry are
  computed deterministically in Python before any LLM prompt is assembled.
- Verified Domain Grounding (RAG): Tactical concepts are grounded in curated literature
  (Arrigo Sacchi, Marcelo Bielsa, Ralf Rangnick, FA coaching manuals) via vector search.
- Zero-Downtime Reliability: If the Groq API experiences rate limits (429), timeouts,
  or provider outages, a deterministic rule-based engine generates a 100% valid,
  syntactically identical 10-section report directly from tool outputs.
- Fan-Centric UX Translation: Translates complex spatial calculations into interactive
  pitch selections, plain-English "Big Picture" takeaways, and collapsible deep metrics.

2.1. The Domain Challenge & FDE Solution Design
--------------------------------------------------------------------------------
Pressing in modern football is spatial, geometric, and time-critical:
- Compactness: Outfield defenders must compress vertical and horizontal space to
  prevent opponents from finding "pockets" between defensive and midfield lines.
- Cover Shadows: A pressing defender curves their run to block the passing line to an
  opponent behind them, effectively neutralizing two players simultaneously.
- Funneling: Defending units deliberately invite a pass into wide corridors or toward
  the touchline ("using the sideline as an extra defender").

PressLens formalizes these concepts into a deterministic pipeline where Python math
handles physical truth, while the LLM focuses exclusively on synthesizing plain-English
explanations from verified metrics.

2.2. Single-Agent Orchestration vs. Multi-Agent Overengineering
--------------------------------------------------------------------------------
File: backend/app/agent/orchestrator.py
Class: TacticalAgentOrchestrator

A major FDE decision in PressLens was rejecting multi-agent frameworks (e.g., CrewAI,
AutoGPT, LangGraph swarms) in favor of a single, highly focused agent orchestrator.

WHY MULTI-AGENT SWARMS WERE REJECTED:
- Latency & Overhead: Multi-agent conversations incur 4x–8x LLM round-trip latency.
  In a sports analytics context, waiting 20–30 seconds for 5 agents to debate is unacceptable.
- Compounding Errors: When Agent A hallucinates, Agent B accepts it as ground truth,
  compounding errors across the swarm.
- Token Cost & Unpredictability: Autonomous swarms loop unpredictably, burning API tokens
  and generating non-deterministic JSON schemas.

THE PRESSLENS SINGLE-AGENT PATTERN:
TacticalAgentOrchestrator runs a deterministic sequential 4-tool execution pipeline:
1. ContextValidationTool -> Checks data sufficiency and flags limitations.
2. ScenarioInspectionTool -> Extracts team formations, lineups, and ball location.
3. TacticalRelationshipTool -> Computes distances, pressing vectors, compactness, and cover shadows.
4. KnowledgeRetrievalTool -> Retrieves relevant theoretical literature chunks via RAG.
5. Context Assembly -> Merges tool outputs into a structured prompt.
6. Structured LLM Call -> Calls Groq LLM (llama-3.3-70b-versatile) with strict Pydantic schema validation.
7. Resilient Fallback -> Intercepts any LLM failure to emit a deterministic report.

2.3. The 4 Deterministic Tactical Agent Tools
--------------------------------------------------------------------------------
All tools inherit from AgentTool (backend/app/agent/tools/base.py), which enforces:
- `name: str` and `description: str`
- `async def execute(**kwargs) -> ToolResult`
- Standardized `ToolResult` container: `tool_name`, `success`, `data`, `summary`, `error_message`.

TOOL 1: ContextValidationTool
File: backend/app/agent/tools/validation_tool.py
Responsibility: Defensive guardrail preventing hallucination on sparse or corrupted data.
Logic & Execution:
- Validates ball position: Checks if ball coordinates (x, y) exist on the 105m x 68m pitch.
- Validates squad density: Checks if attacking and defending player counts are sufficient.
  - If players < 5 per side: flags missing elements and notes that passing networks cannot be verified.
- Calculates dynamic confidence score & level:
  - High (0.95): >= 10 players per side, ball coordinates verified, zero invalid coordinates.
  - Medium (0.75): >= 5 players per side, ball coordinates verified.
  - Low (0.40): Sparse players, missing ball coordinates, or invalid pitch boundaries.
- Explicit Uncertainty Output: When confidence is Low, the tool mandates that the LLM
  explicitly state analytical uncertainty in the `confidence_and_limitations` section
  rather than fabricating conclusions.

TOOL 2: ScenarioInspectionTool
File: backend/app/agent/tools/scenario_tool.py
Responsibility: Structural data extraction and normalization.
Logic & Execution:
- Parses the scenario payload: Title, match phase (high_press, mid_block, low_block, counter_press),
  tactical situation description, and match context (competition, score, minute).
- Formats squad rosters: Maps player IDs, squad numbers, names, tactical roles (GK, CB, LB, RB, DM, CM, RW, LW, CF),
  and spatial (x, y) coordinates into clean lookup tables for prompt injection.
- Extracts pitch zone metadata: Assigns the ball to one of 18 standard football zones
  (e.g., "Defensive Third - Right Half-space", "Zone 14", "Attacking Third - Wide Flank").

TOOL 3: TacticalRelationshipTool (The Mathematical Core)
File: backend/app/agent/tools/relationship_tool.py
Responsibility: Deterministic spatial geometry, pressing vectors, team compactness, and cover shadow cones.
Implementation Details:
- Euclidean Distance:
  `dist = math.hypot(p1["x"] - p2["x"], p1["y"] - p2["y"])`
- Ball Carrier Identification:
  Iterates over all attacking outfield players, calculates distance to ball (bx, by),
  and identifies the closest player as `ball_carrier`.
- Primary Presser Identification:
  Calculates Euclidean distance from all defending players to the ball carrier.
  The closest outfield defender is classified as `primary_presser`. Defenders within
  15.0m are tagged as `supporting_pressers`.
- Pressing Direction & Funneling Vector:
  Calculates vector `(dx, dy) = (bc_x - presser_x, bc_y - presser_y)`.
  Funnel classification logic:
  - If `bc_y >= 50.0` or `bc_y <= 18.0`: classified as `touchline_lock` (sideline boundary constraint).
  - Else if `abs(dy) > abs(dx)`: classified as `flank_funneling`.
  - Else: classified as `central_compression`.
- Cover Shadow Cone & Passing Lane Interception Algorithm:
  To determine whether a defender casts a cover shadow between the ball carrier (bc_x, bc_y)
  and a teammate receiver (tx, ty), PressLens implements a point-to-segment perpendicular
  projection function: `_point_to_segment_distance(px, py, x1, y1, x2, y2)`.
  - Computes projection scalar `t = ((px - x1)*dx + (py - y1)*dy) / seg_len_sq`.
  - Clamps `t` to `[0.0, 1.0]` to find the closest point `(proj_x, proj_y)` on the segment.
  - Perpendicular distance `dist = math.hypot(px - proj_x, py - proj_y)`.
  - SHADOW RULE: If `0.10 <= t <= 0.90` (defender is physically between carrier and receiver)
    AND `perpendicular distance <= 3.0m`, the passing lane is flagged as `blocked_by_cover_shadow`,
    and the defender's name is appended to `cover_shadow_defenders`.
  - CONTESTED RULE: If not shadowed, but the receiver's distance to the nearest defender <= 3.5m,
    the lane is marked `contested`.
  - OPEN RULE: If neither condition is met, the passing lane is classified as `open`.
- Team Compactness Metrics:
  Extracts bounding coordinates of all outfield defending players:
  `block_length = max(xs) - min(xs)` (vertical pitch depth in meters)
  `block_width = max(ys) - min(ys)` (horizontal pitch width in meters)
  `is_compact = block_length <= 35.0` (modern high-press standard).

TOOL 4: KnowledgeRetrievalTool (RAG Integration)
File: backend/app/agent/tools/knowledge_tool.py
Responsibility: Semantic retrieval of validated coaching theory from PostgreSQL vector storage.
Logic & Execution:
- Accepts query string, optional tactical topic filter (e.g., "high_press", "cover_shadows"),
  and `top_k` (default 4).
- Calls `KnowledgeService.semantic_search_chunks()` to perform vector cosine similarity search.
- Deduplicates sources and constructs structured `SourceCitation` objects:
  `document_title`, `topic`, `author`, `publication`, `relevance_score`.
- Returns both raw text chunks for LLM prompt context and citation models for UI rendering.

2.4. Groq LLM Integration & Provider Resilience (GroqClient)
--------------------------------------------------------------------------------
File: backend/app/integrations/groq_client.py
Class: GroqClient

Groq is integrated via the official asynchronous Python SDK (`groq.AsyncGroq`)
using model `llama-3.3-70b-versatile`.

WHY GROQ & LLAMA 3.3 70B:
- Extreme Inference Speed: Groq's LPU (Language Processing Unit) architecture generates
  structured tokens at 250–300 tokens/sec. This delivers full 10-section analyses in < 2 seconds,
  enabling real-time user experiences.
- Strong Reasoning on Structured Data: Llama 3.3 70B reliably follows complex multi-section
  JSON schemas without dropping keys or drifting into conversational filler.

FDE RESILIENCE MECHANISMS IN GROQCLIENT:
1. Lazy Initialization: `get_groq_client()` validates API key presence on first invocation,
   raising clean `ConfigurationError` instead of crashing application startup.
2. Exponential Backoff with Jitter:
   Catches HTTP 429 (Rate Limit) and HTTP 500/503 (Server Overload):
   `sleep_time = (delay * (2 ** (attempt - 1))) + random.uniform(0.1, 0.5)`
   Retries up to `settings.GROQ_MAX_RETRIES` (3 attempts).
3. Request Timeout Handling:
   Wraps API calls in `asyncio.wait_for(..., timeout=settings.GROQ_TIMEOUT_SECONDS)` (30s).
   Times out cleanly into HTTP 504 `AIProviderError`.
4. Structured Output Enforcement (`chat_completion_structured`):
   Enforces `response_format={"type": "json_object"}`.
   Parses raw JSON string with `json.loads()`.
   Validates strictly against the target Pydantic class: `schema_class.model_validate(parsed_dict)`.
   Catches `json.JSONDecodeError` and Pydantic `ValidationError` separately, logging precise errors.

2.5. Vector Embeddings & RAG Knowledge Pipeline
--------------------------------------------------------------------------------
Files:
- backend/app/services/embedding_service.py (EmbeddingService)
- backend/app/services/knowledge_service.py (KnowledgeService)
- backend/app/models/knowledge_document.py (KnowledgeDocument)
- backend/app/models/knowledge_chunk.py (KnowledgeChunk)

EMBEDDING ENGINE:
- Model: `BAAI/bge-small-en-v1.5` running locally via FastEmbed ONNX runtime.
- Dimensions: 384-dimensional dense float vectors.
- Normalization: Unit L2-normalized (`vec = vec / np.linalg.norm(vec)`), enabling cosine similarity
  to be computed via simple dot product.
- Deterministic Offline Fallback:
  If FastEmbed cannot download weights (e.g. offline environments, air-gapped deployments, tests),
  `_generate_deterministic_fallback()` seeds `np.random.RandomState` using the MD5 digest of the text.
  This produces reproducible, unit-normalized 384-dimensional vectors, guaranteeing the test suite
  and local dev servers operate with 100% offline autonomy.

DOCUMENT CHUNKING STRATEGY:
- In football literature, tactical concepts are tightly coupled with principles and author context.
- `EmbeddingService.chunk_document_content()` prepends document metadata to every chunk:
  `"[Source: {title} | Topic: {topic}] {content}"`
- If tactical principles are defined, they are appended:
  `"Key Principles: 1. ... 2. ..."`
- This guarantees semantic embeddings capture both the theoretical context and author authority.

VECTOR STORAGE & SEARCH IN POSTGRESQL:
- Table: `knowledge_chunks` with column `embedding ARRAY(Float)` (or pgvector column).
- Query: `KnowledgeService.semantic_search_chunks()`
  1. Computes query embedding using `EmbeddingService.generate_embedding(query_text)`.
  2. Queries chunks matching optional topic filter.
  3. Computes cosine similarity in Python/PostgreSQL:
     `EmbeddingService.cosine_similarity(query_emb, chunk.embedding)`
  4. Filters candidates by `min_similarity` (>= 0.30) and returns top `k` (4) chunks sorted descending.

2.7. Structured Pydantic Schema Enforcement (FullTacticalAnalysisReport)
--------------------------------------------------------------------------------
File: backend/app/schemas/analysis.py

The analysis output is governed by a strict 10-section Pydantic model:
1. `situation_overview`: Match phase, tactical situation, attacking/defending team setups,
   ball location summary, and plain-English executive summary.
2. `pressing_strategy`: Intensity level (High, Medium, Intense Counter-Press), primary objective,
   pressing direction/funneling, and unit coordination scheme.
3. `pressing_triggers`: Visual triggers (heavy touch, back-pass), tactical traps (baited pass),
   and primary trigger player.
4. `passing_lane_coverage`: Active cover shadows, directly blocked options, contested options,
   and open escape routes.
5. `tactical_advantages`: Compactness edge, turnover potential, and key tactical advantages.
6. `exposed_spaces`: Rest-defense risks, exposed pitch zones (e.g. weak-side flank), and vulnerabilities.
7. `opposition_responses`: Recommended counter-mechanisms, switch of play feasibility, third-man runs.
8. `fan_watch_points`: Next decisive action to watch, key duel to follow, and memorable tactical takeaway.
9. `confidence_and_limitations`: Confidence score (0.0 to 1.0), confidence level (High/Med/Low),
   data sufficiency status, and explicit analytical limitations.
10. `supporting_sources`: List of `SourceCitation` objects attributing theoretical claims to literature.

- Generates every one of the 10 report sections programmatically using the verified

  and RAG citations.
- Outputs a valid `FullTacticalAnalysisReport` matching the exact schema.

3.3. API Integration Layer & Dynamic Host Resolution (client.ts)
--------------------------------------------------------------------------------

CRITICAL WINDOWS NETWORKING RESOLUTION:
On Windows systems, `localhost` frequently resolves to IPv6 `::1`, while Python/Uvicorn
binds to IPv4 `127.0.0.1`. When browsers connect across mismatched interfaces, connections
are refused.
PressLens implements dynamic host detection:
```typescript
export const getBaseUrl = (): string => {
  const envUrl = import.meta.env.VITE_API_BASE_URL as string | undefined
  if (envUrl && envUrl.trim().length > 0) return envUrl.trim().replace(/\/+$/, '')
  if (typeof window !== 'undefined' && window.location.hostname === '127.0.0.1') {
    return 'http://127.0.0.1:8000/api/v1'
  }
```

--------------------------------------------------------------------------------
6.1. Core Architectural Trade-offs & Decisions
--------------------------------------------------------------------------------

Trade-off 1: In-Process Embeddings (FastEmbed ONNX) vs. Cloud Embeddings API (OpenAI/Cohere)
- Decision: Use `fastembed` with `BAAI/bge-small-en-v1.5` running locally.
- Rationale: Zero network round-trips for embedding generation, zero API costs,
  no external dependency that can fail during matchday operations, and 100% offline capability.

Trade-off 2: PostgreSQL Array Vectors vs. Dedicated Vector Database (Pinecone/Milvus)
- Decision: Store 384-dimensional vectors in PostgreSQL using `ARRAY(Float)` / `pgvector`.
- Rationale: Avoids the operational overhead of managing two databases. Scenarios,
  analyses, conversation history, and tactical chunks remain in a single transactional database,
  allowing ACID transactions and cascade deletions (`ondelete="CASCADE"`).

Trade-off 3: Single-Agent Tool Pipeline vs. Multi-Agent Autonomous Swarms
- Decision: Single orchestrator running deterministic tools sequentially.
- Rationale: Deterministic execution order, sub-2-second latency, zero infinite loops,
  and predictable token consumption. FDEs prioritize reliability over hype.

Trade-off 4: Pure SVG Pitch vs. HTML5 Canvas / WebGL
- Decision: Pure SVG with normalized viewBox="0 0 105 68".
- Rationale: SVG elements exist in the DOM, enabling native React event listeners
  (`onClick`, `onMouseDown`, `hover`), CSS styling, and screen-reader accessibility.
  Since there are only 22 players and 1 ball, Canvas/WebGL would be unnecessary complexity.

6.2. Anticipated Demo Questions & High-Impact Answers
--------------------------------------------------------------------------------

Q1: "Why did you build this with a single agent instead of LangChain or CrewAI?"
Strong Answer:
"In an enterprise production deployment, predictability, latency, and cost are paramount.
Multi-agent swarms introduce non-deterministic conversation loops, 4x higher latency,
and compounding hallucinations. In football tactical analysis, the sequence of operations
is naturally deterministic: you must validate data first, extract lineups second, calculate
spatial geometry third, and retrieve tactical theory fourth.
By building a dedicated `TacticalAgentOrchestrator` with specialized tools, PressLens delivers
sub-2-second response times, 100% schema compliance, and zero runtime loop failures."

Q2: "How do you prevent the LLM from hallucinating coordinates or player distances?"
Strong Answer:
"We enforce a strict separation between deterministic physical math and LLM reasoning.
The LLM is never asked to calculate distances, convex hulls, or angles.
Our Python `TacticalRelationshipTool` computes Euclidean distances, perpendicular point-to-segment
cover shadow cones, and team compactness bounding boxes. These exact numbers are injected into
the prompt context as established physical facts. The LLM's role is strictly confined to
domain synthesis and qualitative tactical explanation."

Q3: "What happens if the Groq LLM API goes down or hits rate limits during a live match?"
Strong Answer:
"PressLens implements a two-tier resilience strategy:
First, `GroqClient` executes exponential backoff with random jitter for transient 429 rate limits
and 500/503 server errors, with a 30-second timeout.
Second, if all retries fail, `TacticalAgentOrchestrator` intercepts the error and routes to
`_build_deterministic_report()`. This rule-based synthesis engine constructs a complete, 100%
grounded 10-section report directly from the deterministic spatial metrics and RAG citations.
The end user receives a high-quality tactical report with zero downtime."

Q4: "How does the RAG pipeline handle football-specific terminology like 'cover shadows'?"
Strong Answer:
"Our vector database is seeded with curated tactical literature from Arrigo Sacchi,
Marcelo Bielsa, Ralf Rangnick, and FA coaching manuals. We chunk documents with contextual
metadata prefixes (`[Source: {title} | Topic: {topic}]`) so embeddings capture tactical nuance.
During retrieval, `KnowledgeRetrievalTool` queries PostgreSQL using 384-dimensional dense vectors
generated by FastEmbed. Matches with cosine similarity >= 0.30 are passed to the prompt,
and every citation is attributed in the report with author, publication, and relevance score."

Q5: "How did you design the user experience for non-technical football fans?"
Strong Answer:
"Sports analytics dashboards often overwhelm users with convex hulls, centroid coordinates,
and raw data tables. In PressLens, we implemented three user-centric features:
1. 'The Big Picture' executive summary leading with 3 quick-glance cards and 'What to Watch Next'.
2. An interactive football pitch where clicking any player, passing lane, pressing trap arrow,
   or compactness block opens an instant plain-English explainer card (`PitchSelectionExplainer`).
3. Collapsible sections with preview badges (`CollapsibleSection`) that keep advanced spatial geometry,
   AI confidence metrics, and academic RAG citations accessible without cluttering the screen."
